# 集群证明接口（当前实现）

## 范围

- `POST /v1/attest/cluster`：对一个集群中的多个 TDX 节点进行证明。
- `POST /v1/attest/cluster/node/{cluster_id}`：对指定集群中的单个 TDX 节点进行证明。
- 两个接口目前不要求登录或 API-KEY，也不校验集群所有者。
- 仅支持 `anymatch`，`cluster_ids` 必须且只能包含一个集群 ID。
- 每个提交节点都必须匹配该集群内至少一条策略，所有节点通过才签发集群令牌。不同节点独立匹配，可以命中同一条策略；不要求覆盖集群的全部策略。
- 集群详情直接内嵌令牌，不写入数据库，不提供详情查询 URL 或 GET 接口。

## 集群证明请求

```json
{
  "mode": "anymatch",
  "cluster_ids": ["已创建的集群 ID"],
  "nonce": "从 /v1/nonce 获取的 nonce",
  "reports": [
    {
      "node_id": "node-1",
      "tee": "tdx",
      "tee_report": "TDX Quote 的标准 Base64 编码",
      "runtime_data": "运行时数据的标准 Base64 编码"
    }
  ]
}
```

`reports` 不得为空，`node_id` 必填且在请求内唯一。`node_id` 是调用方提供的关联标识，不代表经硬件证明的节点身份。

## 集群节点证明请求

```json
{
  "nonce": "从 /v1/nonce 获取的 nonce（可选）",
  "report": {
    "tee": "tdx",
    "tee_report": "TDX Quote 的标准 Base64 编码",
    "runtime_data": "运行时数据的标准 Base64 编码"
  }
}
```

此接口不要求 `node_id`。省略 nonce 时不验证 nonce；仍然执行硬件验签和策略匹配。若提供运行时数据，仍校验其与报告的绑定。

## 报告验证和字段兼容

TDX 硬件验签复用现有验证器，包括 collateral 和吊销检查。只对验签通过的报告执行策略评估。

运行时数据兼容原文档中的 `runtime_date` 和现有字段 `runtime_data`；同时提供非空值时二者必须相同。复用现有客户端绑定约定：

```text
digest = SHA256(UTF8(nonce + runtime_data))
TDX REPORTDATA = UTF8(lowercase_hex(digest))  // 64 字节
```

其中 `runtime_data` 是请求里的 Base64 字符串，不是 Base64 解码后的字节。`runtime_date` 先归一化成该字段。nonce 和运行时数据均未提供时，跳过 REPORTDATA 绑定校验。nonce 的有效期和复用行为沿用现有 nonce 管理器。

`parameter` 可以传递 JSON，由 TDX 验证器处理。当前 TDX 验证器不使用额外参数。

当前不支持其他 TEE、异构外设、init_data 和 event_log 验证；请求包含非空的 `trusted_hetero_devices`、`init_data` 或 `event_log` 时明确拒绝。

## 策略

通过现有集群策略管理接口保存 Base64 编码的 Rego。使用以下输入和查询：

- 输入：`input.trusted_node.tee`、`input.trusted_node.trusted_hetero_devices`。
- 查询：`data.trustnode.match_node`。
- 仅布尔值 `true` 表示命中，`false` 或未定义表示未命中。编译错误、执行错误和非布尔结果使请求失败。

例如：

```rego
package trustnode

default match_node := false

match_node {
    input.trusted_node.tee.type == "tdx"
    input.trusted_node.tee.tdx_mrtd == "允许的 MRTD 十六进制值"
    input.trusted_node.tee.tdx_td_attributes_debug == false
}
```

集群所有策略在证明开始时读取一次，并在节点匹配前编译。每个节点只验签一次，再对所有策略求值；令牌记录该节点所有命中的策略。空策略组不能通过证明。

## 响应和令牌

成功返回 HTTP 200：

```json
{"code":"200","message":"attest successful","token":"ES256 签名的 JWT"}
```

无效 JSON、无效参数、不存在的集群、验签失败和策略不匹配返回 HTTP 400，数据库策略查询失败返回 HTTP 500。错误响应包含字符串 `code` 和 `message`，不包含 token。集群证明失败业务码为 `2009`，节点证明失败业务码为 `2010`。

两个令牌均沿用现有 ES256 签名、CA、有效期配置和通用 JWT claims，并添加 `ver: "1.0.0"`。

集群令牌包含：

```json
{
  "ver": "1.0.0",
  "mode": "anymatch",
  "policy_infos": [{"cluster_id":"...","policies_hash":"..."}],
  "trusted_cluster": {
    "trusted_cluster_hash": "...",
    "cluster_detail": [
      {
        "node_id": "node-1",
        "tee": {"type":"tdx","tdx_mrtd":"..."},
        "trusted_hetero_devices": [],
        "attester_info": {"verify_nonce":"..."},
        "policy_infos": [
          {"cluster_id":"...","policies_hash":"...","policy_id":"...","policy_hash":"..."}
        ]
      }
    ]
  }
}
```

节点令牌包含 `attester_info`（存在已验证的数据时）、`policy_infos`（该节点命中的策略）和 `trusted_node`（tee、trusted_hetero_devices），对应设计文档 A.5。

哈希约定：

1. `policy_hash`：SHA-256(策略的 Base64 Rego 字符串)，与现有策略模型一致。
2. `policies_hash`：按策略 ID 升序排列整个集群的策略，序列化为紧凑 JSON 数组 `[{"policy_id":"...","policy_hash":"..."}, ...]`，计算 SHA-256。
3. `trusted_cluster_hash`：对 `{"cluster_detail": [...]}` 计算 SHA-256。所有层级的对象 key 按字典序排序，数组保留请求顺序，使用 Go `encoding/json.Marshal` 的紧凑 UTF-8 JSON 和默认转义规则，不包含 hash 本身。

所有 hash 均输出小写十六进制字符串。

## 接口文档（调用方使用）

本节对应当前实现，可独立用于客户端接入。示例中的服务地址为 `http://127.0.0.1:8081`；部署时替换为实际地址。包含占位符的 JSON 用于说明结构，真实调用需要填写有效集群 ID、nonce 和硬件 Quote。

### 1. 接口总览与约定

| 用途 | 方法 | 完整路径 | 鉴权 |
| --- | --- | --- | --- |
| 获取 nonce | GET | `/v1/nonce` | 不需要 |
| 多节点集群证明 | POST | `/v1/attest/cluster` | 不需要 |
| 集群内单节点证明 | POST | `/v1/attest/cluster/node/{cluster_id}` | 不需要 |
| 获取 JWT 验签公钥集合 | GET | `/v1/pki/ca` | 不需要 |
| 登录管理账号 | POST | `/v1/user/login` | 用户名、密码 |
| 创建集群策略组 | POST | `/v1/trustedcluster/policygroup` | 登录 token |
| 添加节点策略 | POST | `/v1/trustedcluster/policygroup/{cluster_id}/policy` | 登录 token，集群所有者 |
| 查询集群全部策略 | GET | `/v1/trustedcluster/policygroup/{cluster_id}` | 登录 token，集群所有者 |

通用约定：

- POST 请求使用 `Content-Type: application/json`，JSON 使用 UTF-8。
- 两个证明接口的 `code` 是字符串，例如 `"200"`；登录和 nonce 接口的 `code` 是数字，例如 `200`。客户端应按接口定义处理。
- 硬件报告、运行时数据和上传的 Rego 使用标准 Base64，即 `+`、`/` 字母表及所需的 `=` padding。JWT 的三个分段使用无 padding 的 Base64URL，不能混用两种编码。
- 当前仅支持 `tee: "tdx"`，且验证器仅接受 TDX Quote V4。`tee_report` 编码的是完整二进制 Quote，不是 TDREPORT、JSON 或十六进制文本。
- 集群证明只接受 `mode: "anymatch"` 和一个 `cluster_ids` 元素。`mode` 没有默认值。
- `anymatch` 的含义是：**每个提交节点至少命中集群内一条策略，所有提交节点通过才返回 token**。不同节点可以命中同一条策略，不要求覆盖全部策略。
- 当前接口不会检查一个集群是否还有未提交的实际成员；令牌只证明本次提交的节点集合。
- `node_id` 是调用方提供的关联标识，不是从 TDX 报告提取的硬件身份。当前不会将这个字段自动加入 REPORTDATA，也不会将它传入 Rego。
- 没有详情持久化、详情 GET 接口和 `trusted_cluster_url`。令牌自带本次证明的详情。

### 2. 获取 nonce 和生成报告

#### 2.1 获取 nonce

```bash
export TCAS_URL='http://127.0.0.1:8081'

curl --fail-with-body -sS "$TCAS_URL/v1/nonce" -o nonce-response.json
TCAS_NONCE=$(jq -er '.data.nonce' nonce-response.json)
```

成功响应示例：

```json
{
  "code": 200,
  "message": "get nonce successful",
  "data": {
    "nonce": "831d8dd0add203ac3d8b4fbde75e1152",
    "expired": "2026-09-18T18:03:00+08:00"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.nonce` | string | 原样用于生成报告和提交证明；不再 Base64 编码，不改大小写 |
| `data.expired` | string | 带时区的到期时间，按 RFC 3339 时间解析 |

nonce 默认有效期为 **3 分钟**，由服务配置 `NonceLifeTime` 控制，单位是分钟。生成 Quote 和提交证明须在有效期内完成；准备镜像、策略等耗时操作应先完成，再获取 nonce。

当前 nonce 不与某个用户、集群或接口绑定，也不会在成功后自动消耗，因此有效期内可以复用。它不是一次性令牌或幂等请求 ID。nonce 过期后须获取新 nonce，并使用新 nonce 重新生成报告，不能只修改请求中的 nonce。

#### 2.2 REPORTDATA 绑定协议

先将运行时数据编码为标准 Base64 字符串 `R`；未提供运行时数据时 `R = ""`。将 nonce 作为原字符串 `N`；单节点接口未提供 nonce 时 `N = ""`。

```text
R = Base64(runtime_bytes)
D = SHA256(UTF8(N + R))
REPORTDATA = ASCII(lowercase_hex(D))
```

`N + R` 是直接拼接，中间不加空格、换行、冒号或其他分隔符。输入是 Base64 字符串 `R`，不是其解码结果。最终 REPORTDATA 必须是 **64 字节 ASCII 十六进制文本**；不要将 32 字节原始 digest 加零填充成 64 字节。

| 请求 nonce | 请求运行时数据 | 绑定规则 |
| --- | --- | --- |
| 有 | 有 | `SHA256(nonce + runtime_data)` 的小写 hex 文本 |
| 有 | 无 | `SHA256(nonce)` 的小写 hex 文本 |
| 无 | 有 | `SHA256(runtime_data)` 的小写 hex 文本；仅适用于单节点接口 |
| 无 | 无 | 跳过 REPORTDATA 绑定校验，仍验硬件报告和策略；仅适用于单节点接口 |

下面生成两个节点的运行时数据和 REPORTDATA 文件，不生成硬件 Quote：

```bash
python3 - <<'PY'
import base64
import hashlib
import json
from pathlib import Path

nonce = json.loads(Path("nonce-response.json").read_text())["data"]["nonce"]
for node_id, workload in [("node-1", "worker-a"), ("node-2", "worker-b")]:
    runtime = json.dumps(
        {"node_id": node_id, "workload": workload},
        separators=(",", ":"),
    ).encode("utf-8")
    encoded = base64.b64encode(runtime).decode("ascii")
    reportdata = hashlib.sha256((nonce + encoded).encode("utf-8")).hexdigest()
    Path(f"{node_id}.runtime.b64").write_text(encoded)
    Path(f"{node_id}.reportdata.bin").write_bytes(reportdata.encode("ascii"))
    assert len(reportdata) == 64
PY
```

在对应的 TDX 节点上，通过该节点的 Quote 工具或 SDK，将 `node-1.reportdata.bin`、`node-2.reportdata.bin` 的原始 64 字节分别传入 Quote 生成过程，得到 `node-1.quote.bin`、`node-2.quote.bin`。实际命令取决于安装的工具；本项目接口不代替节点生成 Quote。Quote 生成后不可修改其 REPORTDATA。

将生成的 Quote 收集到请求发起方，再执行：

```bash
python3 - <<'PY'
import base64
from pathlib import Path

for node_id in ["node-1", "node-2"]:
    quote = Path(f"{node_id}.quote.bin").read_bytes()
    Path(f"{node_id}.quote.b64").write_text(
        base64.b64encode(quote).decode("ascii")
    )
PY
```

### 3. 集群证明接口

```http
POST /v1/attest/cluster
Content-Type: application/json
```

#### 3.1 请求字段

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `mode` | string | 是 | 当前只能是 `anymatch`，区分大小写 |
| `cluster_ids` | array[string] | 是 | 长度必须等于 1；对应已存在且有策略的集群 |
| `nonce` | string | 是 | 非空且有效，所有报告使用同一个 nonce |
| `reports` | array[object] | 是 | 至少一个元素；不允许 null 元素 |
| `reports[].node_id` | string | 是 | 非空，且在本次请求内不能重复 |

每份报告的其他字段见第 5 节。

```json
{
  "mode": "anymatch",
  "cluster_ids": ["b57078ec-b921-4531-8a09-d82ee6405af3"],
  "nonce": "831d8dd0add203ac3d8b4fbde75e1152",
  "reports": [
    {
      "node_id": "node-1",
      "tee": "tdx",
      "tee_report": "<node-1的Quote标准Base64>",
      "runtime_data": "<node-1的运行时数据标准Base64>"
    },
    {
      "node_id": "node-2",
      "tee": "tdx",
      "tee_report": "<node-2的Quote标准Base64>",
      "runtime_data": "<node-2的运行时数据标准Base64>"
    }
  ]
}
```

#### 3.2 可执行调用示例

在同一工作目录中完成第 2 节，并设置已有集群 ID：

```bash
export TCAS_CLUSTER_ID='替换为已创建的集群ID'

jq -n \
  --arg cluster_id "$TCAS_CLUSTER_ID" \
  --slurpfile nonce_response nonce-response.json \
  --rawfile quote1 node-1.quote.b64 \
  --rawfile quote2 node-2.quote.b64 \
  --rawfile runtime1 node-1.runtime.b64 \
  --rawfile runtime2 node-2.runtime.b64 \
  '{
    mode: "anymatch",
    cluster_ids: [$cluster_id],
    nonce: $nonce_response[0].data.nonce,
    reports: [
      {node_id: "node-1", tee: "tdx", tee_report: $quote1, runtime_data: $runtime1},
      {node_id: "node-2", tee: "tdx", tee_report: $quote2, runtime_data: $runtime2}
    ]
  }' > cluster-attest-request.json

curl --fail-with-body -sS \
  -X POST "$TCAS_URL/v1/attest/cluster" \
  -H 'Content-Type: application/json' \
  --data-binary @cluster-attest-request.json \
  -o cluster-attest-response.json

jq . cluster-attest-response.json
```

#### 3.3 成功条件和响应

每份 Quote 都必须通过硬件验证、nonce/运行时数据绑定校验，并至少命中一条策略。服务为每个节点评估全部策略，记录所有命中的策略 ID。任一节点失败，整个请求失败，不返回部分成功的 token。

成功返回 HTTP 200：

```json
{
  "code": "200",
  "message": "attest successful",
  "token": "<ES256签名的JWT>"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | 成功固定为 `"200"` |
| `message` | string | 成功固定为 `attest successful` |
| `token` | string | JWT 紧凑格式，内容见第 7、8 节 |

例如 node-2 没有命中策略，返回 HTTP 400：

```json
{
  "code": "2009",
  "message": "node \"node-2\": node does not match any cluster policy"
}
```

### 4. 集群内节点证明接口

```http
POST /v1/attest/cluster/node/{cluster_id}
Content-Type: application/json
```

| 位置 | 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| 路径 | `cluster_id` | string | 是 | 已存在且有策略的集群 ID |
| 请求体 | `report` | object | 是 | 单份 TDX 报告，见第 5 节；不能是 null |
| 请求体 | `nonce` | string | 否 | 非空时必须有效并与报告绑定；省略或空字符串表示不检查 nonce |

此接口不接受 `mode`、`cluster_ids` 或 `policy_ids` 作为策略选择条件；它始终从路径指定的集群加载策略，按“至少命中一条”判断。当前 JSON 解码不会拒绝所有未知字段，但未知字段不具有业务含义。

```json
{
  "nonce": "831d8dd0add203ac3d8b4fbde75e1152",
  "report": {
    "tee": "tdx",
    "tee_report": "<TDX Quote标准Base64>",
    "runtime_data": "<运行时数据标准Base64>"
  }
}
```

以下示例复用第 3 节的 node-1 报告，要求原 nonce 仍有效：

```bash
jq '{nonce: .nonce, report: (.reports[0] | del(.node_id))}' \
  cluster-attest-request.json > node-attest-request.json

curl --fail-with-body -sS \
  -X POST "$TCAS_URL/v1/attest/cluster/node/$TCAS_CLUSTER_ID" \
  -H 'Content-Type: application/json' \
  --data-binary @node-attest-request.json \
  -o node-attest-response.json

jq . node-attest-response.json
```

成功响应外层与集群接口相同，JWT payload 结构见第 9 节。不匹配时返回 HTTP 400：

```json
{
  "code": "2010",
  "message": "node does not match any cluster policy"
}
```

这个接口证明“该报告符合指定集群的节点策略”，不会将节点登记为成员、查询既有集群令牌，也不依赖先调用集群证明接口。

### 5. 通用报告字段

下表同时适用于 `reports[]` 和 `report`：

| 字段 | JSON 类型 | 必填 | 当前实现 |
| --- | --- | --- | --- |
| `node_id` | string | 集群请求必填 | 集群请求中用于关联结果；单节点请求中可省略，提供时也不会写入节点 token |
| `tee` | string | 是 | 仅 `tdx` |
| `tee_report` | string | 是 | 非空标准 Base64，解码后是完整的 TDX Quote V4 |
| `runtime_data` | string | 否 | 原始运行时数据的标准 Base64；非空时检查 REPORTDATA 绑定 |
| `runtime_date` | string | 否 | 原设计字段的兼容别名，与 `runtime_data` 含义相同 |
| `parameter` | 任意 JSON | 否 | 传递给验证器；当前 TDX 验证器不使用，建议省略 |
| `trusted_hetero_devices` | array[object] | 否 | 当前不支持外设验证；省略或空数组，非空时拒绝 |
| `init_data` | string | 否 | 当前不支持；省略或空字符串，非空时拒绝 |
| `event_log` | string | 否 | 当前不支持；省略或空字符串，非空时拒绝 |

`runtime_data` 和 `runtime_date` 同时非空时，字符串必须完全一致；如果只有一个非空，则使用该值。两个值均为空时视为未提供运行时数据。运行时数据原文可以是 JSON 对象、文本或二进制，返回方式见第 10 节。

运行时数据的序列化方式也是绑定的一部分：JSON 空格、字段顺序或换行变化都可能改变 Base64 和哈希。应保存生成报告时使用的 Base64 字符串，并原样提交。

### 6. 策略匹配约定

集群内每条策略都是独立的节点匹配规则，入口为 `data.trustnode.match_node`。输入形状如下：

```json
{
  "trusted_node": {
    "tee": {
      "type": "tdx",
      "tdx_mrtd": "<实际MRTD>",
      "tdx_td_attributes_debug": false
    },
    "trusted_hetero_devices": []
  }
}
```

上例省略其他 TDX 字段，完整字段见第 11 节。`node_id`、nonce 和运行时数据的明文对象不在当前 Rego 输入中；不要在策略里引用不存在的 `input.node_id` 或 `input.attester_info`。

```rego
package trustnode

default match_node := false

match_node {
    input.trusted_node.tee.type == "tdx"
    input.trusted_node.tee.tdx_mrtd == "替换为可信镜像的MRTD"
    input.trusted_node.tee.tdx_td_attributes_debug == false
}
```

评估结果为布尔值 `true` 才命中；`false` 或未定义表示未命中。空策略组、无法编译的 Rego、策略执行错误或非布尔返回值使请求失败，不能被另一条成功策略掩盖。上传接口只检查 Base64 格式，因此上传成功不表示策略语法和语义已经验证。

### 7. JWT 通用结构

token 是签名的 JWT，不是加密对象：

```text
Base64URL(header) + "." + Base64URL(payload) + "." + Base64URL(signature)
```

签名算法为 ES256（ECDSA P-256 + SHA-256），签名覆盖前两个编码分段和中间的点号。调用方使用 JWT 库验证完整 token，不要重新序列化 payload 后自行验签。

#### 7.1 Header

```json
{
  "typ": "JWT",
  "alg": "ES256",
  "jku": "http://127.0.0.1:8081/v1/pki/ca",
  "kid": "<服务签名公钥的标识>"
}
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `typ` | string | 固定 `JWT` |
| `alg` | string | 固定 `ES256`；验签方限定此算法 |
| `jku` | string | 服务配置 `CAURL` 对应的公钥集合地址；调用方使用预先信任的服务地址获取公钥 |
| `kid` | string | 用于在公钥集合中选择对应密钥；作为不透明标识处理 |

#### 7.2 两类 token 都包含的 payload 字段

| 字段 | 类型 | 当前值或含义 |
| --- | --- | --- |
| `ver` | string | 固定 `1.0.0`，证明业务结构版本 |
| `iss` | string | 固定 `trust cluster attestation server` |
| `jti` | string | 本次签发的 UUID；每次签发不同，不是 cluster_id，也不是详情查询 ID |
| `iat` | number | 签发时间，UTC Unix 秒 |
| `exp` | number | 到期时间，UTC Unix 秒 |
| `nbf` | number | 当前实现为 `iat - 1000`，单位秒；不代表报告实际生成时间 |
| `dbgstat` | string | 当前固定 `disabled` 的通用兼容字段，**不是 TDX 调试状态的实测结论** |
| `intuse` | string | 当前固定 `generic` |
| `eat_profile` | string | 当前固定 `not support yet`，不表示已经实现某个 EAT profile |

token 默认有效期为 **15 分钟**，当前复用 `LoginTokenLifeTime` 配置，单位分钟，超过 60 时按 60 处理。调用方以实际 `exp` 为准；服务应配置正数有效期。token 到期与 nonce 到期独立，不能把 token 的有效期理解为 nonce 的有效期。

当前没有 `aud`、`sub` 或 `userId`，不包含调用者身份；它与管理接口登录时得到的 RS256 登录 token 用途不同，不能互换。调用方需检查业务预期的集群、节点和 nonce。策略更新不会自动撤销已签发 JWT；需要以最新策略判定时应重新证明或比对预期的策略组 hash。

| 路径 | 类型 | 说明 |
| --- | --- | --- |
| `mode` | string | 本次证明模式，当前为 `anymatch` |
| `policy_infos` | array[object] | 当前恰好一个元素，描述使用的集群及完整策略组 hash |

| `cluster_detail[].tee` | object | 已通过硬件验证的 TDX 字段，见第 11 节 |
| `cluster_detail[].trusted_hetero_devices` | array | 当前恒为空数组 `[]` |
| `cluster_detail[].attester_info` | object | 本节点的 nonce 和运行时数据结果；集群请求必有 `verify_nonce` |
| `cluster_detail[].policy_infos` | array[object] | 本节点命中的全部策略，至少一个，按 policy_id 升序排列 |

表格中 `cluster_detail[]` 路径均位于 `trusted_cluster` 下。集群 payload 顶层没有 `trusted_node` 或 `attester_info`；读取时应定位到每个节点详情。

### 10. 策略信息和 attester_info

#### 10.1 policy_infos 元素

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `cluster_id` | string | 本次使用的集群 ID |
| `policies_hash` | string | 该集群**全部策略**的快照 hash，包括未被当前节点命中的策略 |
| `policy_id` | string | 命中的具体策略 ID；集群 token 顶层元素不含此字段 |
| `policy_hash` | string | 对应策略的 hash；集群 token 顶层元素不含此字段 |

单节点 token 的 `policy_infos` 和集群详情中每个节点的 `policy_infos` 都含四个字段；同一请求内的 `policies_hash` 相同。token 不携带完整 Rego、策略名或未命中的策略列表，因此不能仅用 token 中命中的策略列表重建整个策略组 hash。

#### 10.2 attester_info

| 字段 | 类型 | 出现条件及含义 |
| --- | --- | --- |
| `verify_nonce` | string | 请求提供了非空 nonce，且服务完成有效期和 REPORTDATA 绑定校验时出现 |
| `runtimedata_json` | object | 运行时原文可解析为非空 JSON 对象时出现，返回解析后的对象 |
| `runtimedata_bin` | string | 运行时原文无法解析为 JSON 对象时出现，返回请求中的原始 Base64 字符串 |

原文为 JSON 数组、字符串、数字、布尔值或普通二进制时，当前均以 `runtimedata_bin` 返回。原文为 `{}` 或 `null` 时，当前由于解析和空值省略行为，不返回 `runtimedata_json`，也不返回 `runtimedata_bin`；绑定校验仍执行。

单节点请求同时省略 nonce 和运行时数据时，整个 `attester_info` 字段省略。如果仅提供可解析为空对象的运行时数据，`attester_info` 可能是 `{}`。不要将“没有 `verify_nonce`”解释为已验证新鲜性。

`runtimedata_json` 是解析后的对象，原始 JSON 的字段顺序、空格和数值文本形式可能丢失。要重新计算 REPORTDATA，应使用本次请求保留的原始 Base64；需要精确保留大整数或标识符时，建议将运行时 JSON 中相应值编码为字符串。

### 11. TDX 验证结果字段

以下字段位于节点 token 的 `trusted_node.tee`，或集群 token 的 `trusted_cluster.cluster_detail[i].tee`。除 `type` 和明确列出的布尔字段外，值均为原始字节的小写十六进制字符串，无 `0x` 前缀。

| 字段 | 类型 / 常规长度 | 含义 |
| --- | --- | --- |
| `type` | string | 固定 `tdx` |
| `tdx_mrtd` | string / 96 hex 字符 | TD 初始构建度量 |
| `tdx_mrseam` | string / 96 hex 字符 | TDX SEAM 模块度量 |
| `tdx_mrsignerseam` | string / 96 hex 字符 | SEAM 模块签名者度量 |
| `tdx_rtmr0` | string / 96 hex 字符 | 运行时度量寄存器 0 |
| `tdx_rtmr1` | string / 96 hex 字符 | 运行时度量寄存器 1 |
| `tdx_rtmr2` | string / 96 hex 字符 | 运行时度量寄存器 2 |
| `tdx_rtmr3` | string / 96 hex 字符 | 运行时度量寄存器 3 |
| `tdx_mrconfigid` | string / 96 hex 字符 | TD 配置标识 |
| `tdx_mrowner` | string / 96 hex 字符 | TD 所有者标识字段 |
| `tdx_mrownerconfig` | string / 96 hex 字符 | 所有者配置标识字段 |
| `tdx_report_data` | string / 128 hex 字符 | REPORTDATA 原始 64 字节的 hex 编码；再 hex 解码后，才得到本协议的 64 字符 SHA-256 文本 |
| `tdx_seam_attributes` | string / 16 hex 字符 | SEAM 属性的原始 8 字节 |
| `tdx_td_attributes` | string / 16 hex 字符 | TD 属性的原始 8 字节 |
| `tdx_td_attributes_debug` | boolean | 当前实现提取的调试位；策略可要求为 false |
| `tdx_td_attributes_key_locker` | boolean | 当前实现从 TD attributes 提取的标志 |
| `tdx_td_attributes_perfmon` | boolean | 当前实现提取的性能监控标志 |
| `tdx_attributes_protection_keys` | boolean | 当前实现提取的 protection keys 标志；注意字段名没有 `td_` |
| `tdx_attributes_septve_disable` | boolean | 当前实现提取的 SEPT-VE disable 标志；注意字段名没有 `td_` |
| `tdx_tee_tcb_svn` | string / 32 hex 字符 | TEE TCB SVN 的原始 16 字节 |
| `tdx_xfam` | string / 16 hex 字符 | XFAM 的原始 8 字节 |
| `tdx_pce_svn` | string / 4 hex 字符 | Quote header PCE SVN 的原始 2 字节 |

这些 hex 字段保持原始字节顺序；涉及整数解释时须按 TDX Quote 格式规定处理字节序。`tdx_mrowner` 等字段不是 TCAS 用户身份。

硬件验签包含 collateral 和吊销检查。运行时事件日志验证尚未实现，RTMR 值出现在 token 中不等于已经验证某份事件日志。`tdx_td_attributes_debug` 是否必须为 false，由集群策略决定；通用 `dbgstat: "disabled"` 不替代该判断。

### 12. 三种 hash 的精确算法

全部使用 SHA-256，输出小写 64 字符 hex。它们用于标识签发时的策略和详情快照，不能替代 JWT 签名验证。

#### 12.1 policy_hash

```text
policy_hash = lowercase_hex(SHA256(UTF8(policy_rego_base64)))
```

输入是数据库保存的 **Base64 Rego 字符串本身**，不是 Base64 解码后的 Rego。修改空格、注释、换行或 Base64 文本都会影响 hash，即使策略语义没有变化。

#### 12.2 policies_hash

读取本次集群全部策略，按 `policy_id` 字符串升序排列，每个元素构造为以下字段顺序：

```json
[
  {"policy_id": "策略ID-1", "policy_hash": "策略hash-1"},
  {"policy_id": "策略ID-2", "policy_hash": "策略hash-2"}
]
```

将数组使用 Go `encoding/json.Marshal` 序列化为无缩进、无额外空格和末尾换行的紧凑 JSON，再计算 SHA-256。**每个对象的字段顺序是 `policy_id` 在前，`policy_hash` 在后**，不要对此对象再次按 key 排序。

策略 ID 和 hash 均为 ASCII。使用第 15 节保存的 `policies-response.json`，可以这样复核：

```bash
python3 - <<'PY'
import hashlib
import json
from pathlib import Path

snapshot = json.loads(Path("policies-response.json").read_text())["policygroup"]
digests = [
    {
        "policy_id": p["policy_id"],
        "policy_hash": hashlib.sha256(p["rego"].encode("utf-8")).hexdigest(),
    }
    for p in sorted(snapshot, key=lambda item: item["policy_id"])
]
encoded = json.dumps(digests, separators=(",", ":")).encode("utf-8")
print(hashlib.sha256(encoded).hexdigest())
PY
```

查询时策略可能已被更新。要验证历史 token，必须保存与签发时一致的完整策略快照；使用当前查询结果不一定匹配历史 hash。

#### 12.3 trusted_cluster_hash

取集群 token 的完整 `trusted_cluster.cluster_detail` 数组，包装成以下对象：

```text
{"cluster_detail": <完整数组>}
```

此处计算的是详情，包含每个节点的 `node_id`、`tee`、外设数组、`attester_info` 和命中策略。不要删除空数组、增加省略字段、改变节点顺序或只选择部分 TDX 字段。hash 不包含 `trusted_cluster_hash` 自身，也不包含顶层的 `iat`、`jti`、`mode` 等字段。

服务先将详情转换为通用 JSON 对象，再使用 Go `encoding/json.Marshal`：所有层级对象的 key 按字典序排序，数组顺序保持不变，默认转义 `<`、`>`、`&`、U+2028 和 U+2029；数值使用 Go 对 `float64` 的 JSON 序列化规则。此算法不是 RFC 8785，不能直接假定其他语言的 `sort_keys` 或 JSON canonicalization 输出完全相同。

以下 Go 程序可按当前服务规则复核。保存为 `verify-cluster-hash.go`，输入为第 13 节验签后输出的完整 payload：

```go
package main

import (
    "crypto/sha256"
    "encoding/json"
    "fmt"
    "os"
)

func main() {
    if len(os.Args) != 2 {
        panic("usage: go run verify-cluster-hash.go cluster-claims.json")
    }
    raw, err := os.ReadFile(os.Args[1])
    if err != nil { panic(err) }
    var claims map[string]interface{}
    if err := json.Unmarshal(raw, &claims); err != nil { panic(err) }
    cluster, ok := claims["trusted_cluster"].(map[string]interface{})
    if !ok { panic("not a cluster token") }
    details, ok := cluster["cluster_detail"].([]interface{})
    if !ok || len(details) == 0 { panic("missing cluster_detail") }
    encoded, err := json.Marshal(map[string]interface{}{"cluster_detail": details})
    if err != nil { panic(err) }
    got := fmt.Sprintf("%x", sha256.Sum256(encoded))
    expected, ok := cluster["trusted_cluster_hash"].(string)
    if !ok || got != expected { panic("trusted_cluster_hash mismatch") }
    fmt.Println("trusted_cluster_hash verified:", got)
}
```

### 13. 公钥获取与 JWT 验签

`GET /v1/pki/ca` 直接返回 JWKS 对象，没有 `code` 或 `data` 外层：

```json
{
  "keys": [
    {
      "kty": "EC",
      "crv": "P-256",
      "kid": "<与JWT header中的kid相同>",
      "x": "<公钥X坐标Base64URL>",
      "y": "<公钥Y坐标Base64URL>",
      "alg": "ECDSA",
      "x5c": ["<DER证书的标准Base64>"]
    }
  ]
}
```

当前服务将 JWK 的 `alg` 写为 X.509 算法名 `ECDSA`，JWT header 则为 `ES256`。部分自动 JWKS 客户端会因此拒绝该密钥。下面的示例从公钥坐标构造 EC 密钥，并明确限定 JWT 算法为 ES256，以兼容当前响应。

公钥来源须是调用方预先信任的服务地址或预置文件。JWT header 中的 `jku` 在验签前不可信，不应直接根据任意 token 的 `jku` 下载并信任新密钥。以下本地 HTTP 地址仅用于演示；部署时使用受信任的公钥分发配置。

```bash
curl --fail-with-body -sS "$TCAS_URL/v1/pki/ca" -o trusted-jwks.json
python3 -m pip install 'PyJWT[crypto]>=2,<3'
```

保存下面的代码为 `verify-token.py`。它验证签名、时间、签发方、版本、集群 ID 和预期 nonce，输出验签后的 payload：

```python
import json
import sys
from pathlib import Path

import jwt
from jwt.algorithms import ECAlgorithm

if len(sys.argv) not in (3, 4):
    raise SystemExit("usage: verify-token.py response.json cluster_id [expected_nonce]")

response_path, expected_cluster = sys.argv[1:3]
expected_nonce = sys.argv[3] if len(sys.argv) == 4 else None
response = json.loads(Path(response_path).read_text())
if response.get("code") != "200":
    raise ValueError("attestation request did not succeed")
token = response["token"]
header = jwt.get_unverified_header(token)
if header.get("alg") != "ES256" or header.get("typ") != "JWT":
    raise ValueError("unexpected JWT algorithm or type")

jwks = json.loads(Path("trusted-jwks.json").read_text())
keys = [k for k in jwks["keys"] if k.get("kid") == header.get("kid")]
if len(keys) != 1:
    raise ValueError("kid is unknown or ambiguous")
key = keys[0]
if key.get("kty") != "EC" or key.get("crv") != "P-256":
    raise ValueError("expected an EC P-256 key")
public_key = ECAlgorithm.from_jwk(json.dumps({
    field: key[field] for field in ("kty", "crv", "x", "y")
}))
claims = jwt.decode(
    token,
    public_key,
    algorithms=["ES256"],
    issuer="trust cluster attestation server",
    options={"require": ["iss", "iat", "exp", "nbf", "jti", "ver", "policy_infos"]},
)
if claims["ver"] != "1.0.0":
    raise ValueError("unsupported attestation version")

infos = claims["policy_infos"]
if not isinstance(infos, list) or not infos:
    raise ValueError("missing policy information")
if any(p["cluster_id"] != expected_cluster for p in infos):
    raise ValueError("unexpected cluster_id")

is_cluster = "trusted_cluster" in claims
is_node = "trusted_node" in claims
if is_cluster == is_node:
    raise ValueError("ambiguous or unknown attestation token")
if is_cluster:
    if claims.get("mode") != "anymatch" or len(infos) != 1:
        raise ValueError("unexpected cluster mode or policy group count")
    nodes = claims["trusted_cluster"]["cluster_detail"]
    if not isinstance(nodes, list) or not nodes:
        raise ValueError("empty cluster detail")
    for node in nodes:
        matches = node["policy_infos"]
        if not matches or any(
            p["cluster_id"] != expected_cluster
            or p["policies_hash"] != infos[0]["policies_hash"]
            for p in matches
        ):
            raise ValueError("inconsistent node policy information")
else:
    nodes = [claims]

if expected_nonce is not None:
    if any(n.get("attester_info", {}).get("verify_nonce") != expected_nonce for n in nodes):
        raise ValueError("nonce missing or different from this request")

print(json.dumps(claims, ensure_ascii=False, indent=2))
```

调用示例：

```bash
TCAS_NONCE=$(jq -er '.data.nonce' nonce-response.json)

python3 verify-token.py cluster-attest-response.json "$TCAS_CLUSTER_ID" "$TCAS_NONCE" \
  > cluster-claims.json

python3 verify-token.py node-attest-response.json "$TCAS_CLUSTER_ID" "$TCAS_NONCE" \
  > node-claims.json

go run verify-cluster-hash.go cluster-claims.json
```

调用方还应将集群详情的节点 ID 集合、节点数量和 runtime_data 中的业务数据与本次请求对应，按业务需要比较允许的策略 ID / hash。上述验签脚本不替代这些业务判断。对于提交了 nonce 的请求，必须传入预期 nonce；有意省略 nonce 的单节点请求，才省略脚本的第三个参数。

密钥轮换后若出现未知 `kid`，从同一受信任来源刷新公钥；需要长期验证历史 token 时，应保留相应的历史验证公钥。当前接口返回当前 CA 对应的密钥。

### 14. 错误响应与处理

以下为两个证明接口的业务错误；HTTP 状态与 JSON `code` 是两个不同概念：

| HTTP 状态 | `code`（string） | 场景 | 调用方处理 |
| --- | --- | --- | --- |
| 200 | `200` | 证明成功 | 验证 token 后使用 |
| 400 | `1105` | 无效 JSON、字段 JSON 类型不符 | 修正序列化和字段类型 |
| 400 | `3005` | 缺失参数、多个集群、不支持的 mode/TEE、重复 node_id、非法 Base64、运行时别名冲突或不支持的非空字段 | 修正请求 |
| 400 | `3014` | 指定集群不存在 | 检查 cluster_id |
| 500 | `3014` | 集群或策略数据库查询失败 | 服务恢复后重试；nonce 过期需重新采集报告 |
| 400 | `2009` | 集群证明失败，包括空策略、策略错误、硬件验证、nonce、绑定、匹配或 token 生成错误 | 根据 message 排查；不会返回部分 token |
| 400 | `2010` | 集群内单节点证明失败，原因范围同上 | 根据 message 排查 |

典型错误消息片段：

| 消息片段 | 含义 |
| --- | --- |
| `only mode anymatch is supported` | 当前不支持 allmatch 或其他模式 |
| `cluster_ids must contain exactly one cluster ID` | 集群数组为空、元素数量错误或 ID 为空白 |
| `duplicate node_id` | 请求内节点标识重复 |
| `cluster has no policies` | 先添加至少一条有效节点策略 |
| `nonce ... is not exist` | nonce 不是该服务签发或已不可用 |
| `nonce is expired` | 获取新 nonce，并重新生成所有受影响的 Quote |
| `userData is not correct` | 检查 nonce、原始 Base64 运行时数据、拼接方式和 64 字节 ASCII REPORTDATA |
| `node does not match any cluster policy` | 已验证的节点字段未满足任意策略 |
| `match_node must be boolean` | Rego 入口返回值类型错误 |
| `verify tee report failed` / `quote verification failed` | 硬件 Quote、签名或 collateral/吊销验证失败 |

集群请求的错误通常带 `node "...":` 前缀，便于定位节点。`message` 用于诊断，可能带验证库返回的细节，不建议将完整文本作为稳定的程序分支条件。

两个证明接口暂不返回鉴权失败；管理接口仍可能返回 401。nonce 接口生成失败时使用其原有数字业务码 `2003`。代理或 Web 框架返回的错误可能不具有上述 JSON 格式，客户端应先检查 HTTP 状态和响应内容类型。

### 15. 从零准备集群和策略

本节应在获取 nonce 前完成。已有集群、策略和管理 token 时，可跳过相应步骤。命令依赖 Bash、curl（支持 `--fail-with-body`）、jq；第 2、12、13 节还分别使用 Python 3、Go 和 PyJWT。

#### 15.1 登录

使用具有策略管理权限的账号，用户名和密码在请求中均需标准 Base64 编码。字段名为 `userName`、`passWord`：

```bash
export TCAS_URL='http://127.0.0.1:8081'
read -r -p '用户名: ' TCAS_USER
read -r -s -p '密码: ' TCAS_PASSWORD
printf '\n'

jq -n --arg user "$TCAS_USER" --arg password "$TCAS_PASSWORD" \
  '{userName: ($user | @base64), passWord: ($password | @base64)}' \
  | curl --fail-with-body -sS \
      -X POST "$TCAS_URL/v1/user/login" \
      -H 'Content-Type: application/json' \
      --data-binary @- -o login-response.json

TCAS_LOGIN_TOKEN=$(jq -er '.token' login-response.json)
unset TCAS_PASSWORD
```

#### 15.2 创建集群

现有管理接口的 `Authorization` 直接使用登录 JWT，**不加 `Bearer ` 前缀**。集群名在当前用户下须唯一：

```bash
curl --fail-with-body -sS \
  -X POST "$TCAS_URL/v1/trustedcluster/policygroup" \
  -H "Authorization: $TCAS_LOGIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"cluster_name":"tdx-demo-cluster"}' \
  -o cluster-response.json

export TCAS_CLUSTER_ID=$(jq -er '.cluster_id' cluster-response.json)
```

成功响应：

```json
{
  "code": "200",
  "message": "success",
  "cluster_id": "b57078ec-b921-4531-8a09-d82ee6405af3"
}
```

#### 15.3 上传策略

将第 6 节的 Rego 保存为 `tdx-node.rego`，将 MRTD 占位值替换为可信镜像的实际度量。两个节点使用不同镜像时，可以分别上传两条策略，或写一条允许两个 MRTD 的规则。

```bash
jq -n --rawfile rego tdx-node.rego \
  '{policy_name: "allowed-tdx-image", policy_rego: ($rego | @base64)}' \
  > policy-request.json

curl --fail-with-body -sS \
  -X POST "$TCAS_URL/v1/trustedcluster/policygroup/$TCAS_CLUSTER_ID/policy" \
  -H "Authorization: $TCAS_LOGIN_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @policy-request.json \
  -o policy-response.json
```

成功响应包含 `policy_id`：

```json
{
  "code": "200",
  "message": "success",
  "policy_id": "de280670-c43b-49d9-a27e-9d359c1d8940"
}
```

查询并保存完整策略组，供第 12 节复核 hash：

```bash
curl --fail-with-body -sS \
  "$TCAS_URL/v1/trustedcluster/policygroup/$TCAS_CLUSTER_ID" \
  -H "Authorization: $TCAS_LOGIN_TOKEN" \
  -o policies-response.json
```

成功响应中的数组字段是 `policygroup`，每个元素为 `{ "rego": "<Base64策略>", "policy_id": "...", "policy_name": "..." }`。读取字段叫 `rego`，上传字段叫 `policy_rego`。
